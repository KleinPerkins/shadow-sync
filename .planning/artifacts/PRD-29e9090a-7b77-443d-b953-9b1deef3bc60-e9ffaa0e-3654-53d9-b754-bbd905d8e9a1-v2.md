# ShadowSync requirements baseline

This v2 successor applies [ADR 0005](../../docs/adr/0005-governed-safety-release-without-controller-rebinding.md) only to the AWA release route; all other requirements and gates remain unchanged.

## Extraction and identity

| ID | Requirement | Required evidence |
|---|---|---|
| REQ-EX-01 (EX-01) | Publish only an allowlisted, transformed product snapshot into fresh public history; import no private or unrelated history. | Complete path/mode/hash manifest, transformation review, and exact output-tree verification. |
| REQ-EX-02 (EX-02) | Keep private source identity and sensitive review evidence outside the public repository while publishing sanitized target and third-party provenance. | Private receipt plus public provenance with no private topology or self-referential tree claim. |
| REQ-EX-03 (EX-03) | Use proprietary source-visible licensing and preserve all third-party license and notice obligations. Binary permission remains separate. | License review, notice inventory, bundle inclusion, and asset provenance. |
| REQ-EX-04 (EX-04) | Use `shadow-sync`, `ShadowSync`, and `com.kleinperkins.shadow-sync` for active identity; allow legacy identifiers only in exact migration, fixture, or historical-reader entries. | Full tracked/generated/binary identity scan and explicit exception ledger. |

## Governance and CI

| ID | Requirement | Required evidence |
|---|---|---|
| REQ-GV-01 (GV-01) | Limit the standard GitHub-hosted runner exception to the intended public ShadowSync repository; do not modify unrelated runnerless policies or controller fleets. | Accepted policy classification and settings read-back. |
| REQ-GV-02 (GV-02) | Use free standard hosted runners, read-only defaults, full action pins, bounded artifacts, and no paid/self-hosted/larger runners. | Workflow inspection, settings evidence, and billing-control verification. |
| REQ-GV-03 (GV-03) | The reviewer App alone approves eligible ordinary exact heads and arms native squash auto-merge; ordinary implementation has no generic operator review gate. | Positive exact-head merge plus stale-head, race, missing-check, untrusted-author, and protected-path refusals. |
| REQ-GV-04 (GV-04) | Protected automation and administration remain owner/admin controlled; release approval and UAT remain separate. | CODEOWNERS/ruleset/environment read-back and negative privilege tests. |
| REQ-GV-05 (GV-05) | Mandatory CI includes quality, compile, runtime safety, native/lifecycle, package contract, and an always-evaluated aggregate gate. | Stable suite roster and exact-head receipts proving no missing, skipped, cancelled, failed, or zero-test mandatory result. |

## Safety and external policy

| ID | Requirement | Required evidence |
|---|---|---|
| REQ-SF-01 (SF-01) | Git operations remain fast-forward-only and refuse dirty, diverged, wrong-origin, invalid-ref, hook/filter, and race conditions. | Positive fixture transactions and negative mutation/ref/config matrices. |
| REQ-SF-02 (SF-02) | Required policy is verified before candidate metadata access, selection, authority changes, hydration, or later admission; any uncertainty fails closed. | Zero-target-access evidence on every malformed, missing, stale, incompatible, or matched-policy refusal. |
| REQ-SF-03 (SF-03) | Preserve P4: verify the governed AWA v1.8.2 hard-no-touch maintenance release through ADR 0005's one-time audited release route, exact pin/runtime, concrete policy/binding, and compatible consumer before installed activation. Controller deployment is not required for this one release. | Source-bound independent review, full verification, protected and sealed maintenance merge, immutable release, pin, runtime, policy, and consumer evidence; no substituted App-check claims. |
| REQ-SF-04 (SF-04) | Never copy the external matcher or use a permissive fallback; preserve visible disabled protected rows and typed bounded adapter behavior. | Contract/parity tests against the verified external implementation and negative adapter tests. |
| REQ-SF-05 (SF-05) | Cancellation, process ownership, locks, leases, child reaping, cleanup, and concurrent admission remain bounded and identity-checked. | Cancellation/fault/lock-contention matrices with cleanup-completion receipts. |
| REQ-SF-06 (SF-06) | Public automation uses only disposable fixtures and never reads real inventory, credentials, installed state, screenshots, or protected targets. | CI isolation tests and disclosure-safe artifacts. |
| REQ-SF-07 (SF-07) | Preview is not mutation authority; checked-out targets may use bounded unknown-relation preview only when mutation freshly classifies them. Operation evidence is operation-scoped, session evidence never substitutes, historical reports are read-only owners, and outcomes derive from durable evidence. | Preview/mutation separation, stale-session refusal, operation-scope, historical-report, and durable-outcome tests. |

## Installation, migration, and update

| ID | Requirement | Required evidence |
|---|---|---|
| REQ-MG-01 (MG-01) | A signed bundled lifecycle coordinator is the sole production authority for install, migration, repair, removal, replacement, and update coordination. | Publisher/signature checks and fault-injected lifecycle suites. |
| REQ-MG-02 (MG-02) | Production setup is source-free and compiler-free; source installers refuse production mutation. | Clean setup with source/compiler unavailable and negative source-installer tests. |
| REQ-MG-03 (MG-03) | Preserve one effective operation authority and recognized user data through transactional identity/state migration; refuse conflicts or malformed/newer data without reset. | Exact migration, concurrent-attempt, interruption, malformed-state, and retry matrices. |
| REQ-MG-04 (MG-04) | Startup remains explicit normal Login Item opt-in; legacy registration is not transferred or recreated silently. | Native startup/remove/opt-in/logout-login evidence. |
| REQ-MG-05 (MG-05) | Sparkle 2.10.1 is the initial sole normal updater after identity establishment; every replacement path is coordinator-gated and signature verified. | Pin verification plus wrong-key, tampered, stale-build, interruption, coordinator-death, and retry tests. |
| REQ-MG-06 (MG-06) | Before readiness commit, recover verified preimages to a stopped state; after commit, repair forward unless downgrade compatibility is proved. | Transaction-cut recovery matrix and state-preservation evidence. |
| REQ-MG-07 (MG-07) | Before live migration, complete source-authority handoff and disable production mutation by the source installer. At the verified identity transition, stop and remove the old launch identity before admitting the new one. | Authority-handoff evidence, negative source-installer production tests, transaction ordering, and proof that no old launch route remains active when the new identity is admitted. |
| REQ-MG-08 (MG-08) | Retain migration readers, compatibility wrappers, and non-executable recovery archives for at least two verified standalone releases and 90 days; retire those compatibility facilities only through a separate retirement record. The retention window does not authorize an active old launch route. | Migration/update coverage, known-installation review, elapsed window, compatibility-retirement evidence, and proof that retained recovery artifacts cannot launch or reactivate the legacy identity. |

The MG-03/MG-06 transaction evidence must additionally prove installer closure, top-level namespace exclusion without lock upgrade, canonical legacy-app retirement, identity-verified process reaping, and an atomic same-directory rename that preserves all log/lock inodes. A copied or newly created lock set cannot satisfy migration or rollback. This closes the legacy pathname re-resolution race before installed qualification.

## Release and acceptance

| ID | Requirement | Required evidence |
|---|---|---|
| REQ-RL-01 (RL-01) | Initial support is macOS 26 arm64, deployment target 26.0, Swift tools 6.2, and Xcode 26.6. Do not claim Intel, universal, macOS 15, or macOS 27 support. | Package/binary/platform inspection and native minimum-version qualification. |
| REQ-RL-02 (RL-02) | `0.10.0` build `15` is the first signed migration candidate; `0.10.1` build `16` is the first independently signed installed-update proof; build numbers are monotonic and never reused. | Release metadata and candidate allocation records. |
| REQ-RL-03 (RL-03) | Distributed applications must be Developer ID signed, hardened, timestamped, notarized, stapled, Gatekeeper-accepted, immutable, and traceable to exact source and dependencies. | Downloaded-asset verification, signing/notarization receipts, checksums, notices, and attestation. |
| REQ-RL-04 (RL-04) | Use a product-specific update key, protected beta/stable feeds, identical-byte promotion, and no signature-verification bypass. | Independent update signature verification, immutable asset/feed evidence, and promotion checks. |
| REQ-RL-05 (RL-05) | Keep source publication, CI operation, signed release, clean installation, migration, installed update, channel promotion, retirement, and UAT as separate completion states. | Separate governed evidence for each state. |
| REQ-RL-06 (RL-06) | UAT closes only by explicit operator acceptance against recorded criteria; merge, screenshots, installation, or isolated observations are evidence, not acceptance. | Recorded UAT decision referencing the tested candidate and criteria. |

## Requirement identity and accountability

The canonical `REQ-` identifiers retain the accepted package IDs in parentheses. The prefix is a documentation-schema adaptation, not a scope change. The extraction architect owns EX; the release engineer and repository administrator own GV; the application engineer and external policy owners own SF; the macOS architect owns MG; the release engineer owns RL-01–05, and the operator owns RL-06. The phase plan binds these groups to dependencies and completion gates.
