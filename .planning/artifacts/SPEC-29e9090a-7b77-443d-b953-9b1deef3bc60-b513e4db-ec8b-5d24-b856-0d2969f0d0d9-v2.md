# Runtime fixture custody and qualification

This component closes the runtime-executor lifetime gap found during P3-CI-01/P3-CI-03 qualification. The application engineer owns the testing-only guardian and fixture owners; the release engineer owns its executor and coverage receipts. REQ-GV-06, REQ-GV-07, REQ-GV-08, REQ-GV-11, REQ-SF-04, REQ-SF-05 and REQ-RL-05 remain governed by approved PRD v4 and PLAN v4. Predecessor technical contracts remain unchanged except the adopted MVP source-publication sequencing and explicit milestone applicability; other requirements and release gates remain in the current parent records.

## Boundary and fixed interface

The runtime suite process is the guardian for its complete assertion bodies and actual child processes. It preserves direct-parent, descriptor-inheritance, process-group, nested TERM/KILL and exclusive-reaping assertions. It accepts one registered suite ID, the already validated testing application identity, inherited control/status channels, and a bounded monotonic work deadline. It accepts no arbitrary command, script or executable request. Qualification fixtures have a separate closed selector roster. Entry is testing-only, before fixture or repository admission. Production binaries exclude both entrypoints and implementation.

The boundary covers executor disappearance, explicit cancellation, deadline expiry, output/transport failure and ordinary assertion failure. It does not claim containment if the guardian itself is forcibly killed. Production suspended-spawn and coordinator integration remain separate qualification gates. The existing descendant-free M5 helper and its zero hard process limit remain unchanged.

## Admission and custody

Validate exact arguments, channel ownership/type/access, descriptor non-aliasing, close-on-exec behavior, deadline bounds and source/binary bindings before readiness. Control and status are nonblocking. The independent control loop cannot wait on assertion or child-owner locks. EOF, malformed control, cancellation and deadline permanently close case/spawn/resume admission. An interrupted case cannot report success, and no later case can start.

Reserve a bounded in-flight spawn slot before the system call. An operation already admitted when cancellation crosses the system call must register its successful original child immediately, before fallible identity capture or publication, and drain without resuming it. Failed spawns release only their reservation. Pending reservations prevent a cleanup-complete result. Registry callbacks execute outside the registry lock; deliberately paused signal/reap tests cannot block control observation.

Retain actual spawn anchors and their transferred owners. Never construct custody from a PID, pathname, journal or process-table search. Normal assertions and emergency cleanup share the same owner and reaping state. A transferred owner is retained even when later validation throws. Never signal after reap, discard unresolved custody at a deadline, or manufacture absence from an observer error.

Before transfer, only the successful original never-resumed spawn may be killed and reaped. After transfer, use the existing owner methods for verified TERM/KILL escalation, stream/group drainage and sole leader reap. Keep the narrowly scoped original-spawn fallback used by injected ownership-failure fixtures; it must prove the actual child was reaped and cannot become a production PID-adoption path. A terminal leader remains held while descendants exist. Retain ownership objects without retaining extra control writers, lease copies or mapping descriptors that would invalidate EOF and inherited-lock tests.

The initial implementation registers the identified M4 group, owner-ordering and spawn-anchor fixtures; M6 inherited-continuity, initialization crash, descriptor-inheritance/collision and parent-loss fixtures. The parent-loss worker has its own bounded pre-readiness/lifetime path while preserving intentional abrupt termination after target readiness. Existing custodian/registry fixtures request cleanup through their own contracts, never by killing the custodian. Every mandatory runtime suite uses the guardian-aware executor; full cancellation coverage for another suite requires explicit registration/evidence, not inference from this list.

## Executor and evidence

The executor retains its direct guardian handle and drains bounded stdout/stderr/status. On timeout, overflow, transport failure, exception or interrupt it sends cancellation or closes control and continues observing. It never applies ordinary TERM/KILL timeout cleanup to the guardian. Unresolved cleanup is a red pending result with the responsible owner retained, not success, absence or permission to launch duplicate work. A later observer cannot signal or adopt a recorded PID.

Success requires all of: exact current source and binary digests; reviewed isolation profile/canaries; exact compiled suite/case inventory; every expected case exactly once; no skipped, failed, cancelled or zero-case coverage; valid terminal status; zero in-flight reservations; every registered child actually reaped with required descendant/stream drainage; and the executor's own guardian reap. Suite exit alone cannot establish descendant cleanup. Missing/duplicate/malformed/out-of-order status or cleanup evidence fails closed. Raw failures and retries are retained separately.

Local suites whose assertions observe a shared temporary namespace run serially. Hosted shards may run on separate disposable workers, preserving the accepted full-inventory and aggregate-gate rules. Qualification receipts distinguish exact current-source execution from older component results. No real host inventory, protected repository, user configuration, installed state or real network remote is a fixture.

## Verification and implementation sequence

1. Implement the bounded admission/custody state and guardian-aware executor under testing-only gates. Test closed input, capacity, permanent cancellation, in-flight registration, no next-case success, independent control observation and pending cleanup without child termination.
2. Register real M4/M6 original spawns and transferred owners; remove raw post-reap group signalling. Preserve every existing case/result label and descriptor assertion. Verify source and production exclusion before native execution.
3. In disposable fixtures, exercise executor loss/deadline before spawn, during admitted spawn, after registration, after transfer/before resume, while running, with terminal leader/live descendant, and during final reap. Verify never-resumed marker absence, unchanged effective lock ownership until drainage, nested TERM/KILL, concurrent cancellation/finalization, unrelated child preservation, and descriptor isolation.
4. Independently review the actual implementation and executor. Run focused native qualification, then the entire registered current-source runtime roster. A partial case or older binary cannot satisfy that gate. Requalify other affected native suites and production exclusion; retain outstanding production and installation gates separately.

This is an incremental implementation contract, not acceptance of a new product feature or a replacement extraction plan. Reviewed sanitized source may be published before runtime/install qualification under the MVP-first decision. The disclosure/provenance gate and all applicable required checks remain mandatory; public source is explicitly not install-ready until runtime, safety, signing and migration gates pass. Every delivered change binds this specification, parent requirements, exact tests and independent review. Recovery is a reviewed source revert or a new private candidate; no installed application or user data changes are part of this component.
