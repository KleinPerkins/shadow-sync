# Native fixture lifetime and qualification contract

This specification implements the existing P3-CI-01 registration/isolation scope and P3-CI-03 qualification gate. It does not change product behavior, widen OS support, authorize live inventory, replace physical UAT, or accept a failed probe. Existing WorkerSession cancellation and takeover assertions remain mandatory.

## Requirements and owner

The application engineer owns the testing-only fixture process and existing callers. The release engineer owns the bounded native executor, negative tests, exact coverage and evidence retention. REQ-GV-06, REQ-GV-07, REQ-GV-08, REQ-GV-11, REQ-SF-04, REQ-SF-05 and REQ-RL-05 remain governed by approved PRD v3 and PLAN v3. All other requirements remain in the parent plan. The earlier foreground/Quit design remains unchanged.

## Closed helper protocol

The testing application exposes one early, testing-only helper route before lifecycle or AppKit admission. It accepts only a closed behavior (`ignore-term` or `default-term`), an inherited liveness-read descriptor, an inherited readiness-write descriptor, and a bounded lifetime (1–30 seconds). It accepts no command, source text, repository path, environment injection or arbitrary executable. Production contains neither this route nor its implementation.

The fixture launcher executes the same testing binary through the system sandbox launcher, adding a helper profile that denies process creation. The outer executor still denies the real account home, external network and writes outside its fresh owner-private fixture root. Its process-exec allowlist contains only the exact testing binary and system sandbox launcher. Policy canaries prove the denials before qualification; inability to establish the sandbox fails the run.

Each helper starts in its own process group. Spawn uses CLOEXEC-by-default and explicit descriptor actions; duplicate source descriptors above the reserved channel numbers before mapping them to avoid clobbering. No helper inherits the parent's liveness-write end or another fixture's lease. Readiness is emitted only after signal behavior and descriptor validation. Missing/malformed readiness or deadline expiry fails launch and triggers owned cleanup.

The helper exits on liveness EOF, an invalid channel or its monotonic absolute deadline even if SIGTERM is ignored. The fixed loop performs no repository, filesystem, network or child-process work. A nested-fork-denial canary must run before readiness; if it unexpectedly creates a child, reap that exact child and fail. This prevents untracked helper descendants without removing real process-group and signal behavior from the tests.

## Ownership and cleanup

A single synchronized fixture owner owns waitpid and records the terminal status once. Background delivery of that result to WorkerSession and deferred cleanup share this owner; they must never compete in independent waitpid loops. Cleanup first closes the lease. Any signal must target the exact unreaped child, with current process identity checked while the same ownership lock excludes reaping. Once reaped, never signal the old PID or group. A cleanup timeout is failure, not evidence of absence.

The existing single-flight test still proves nine concurrent callers share one cancellation/TERM/KILL attempt and one stable outcome; retain the boundary-publication and timeout-fallback races. The takeover test still proves duplicate takeover requests share the token, await a verified stop and invoke the callback once. Replace only their helper construction, readiness and owned cleanup, including the former global temporary readiness file.

Record a bounded append-only `shadow-sync-native-fixture/v1` journal beneath the already validated fixture root. Every successful spawn receives an identity record (PID, group, UID, start time, executable, generation); a matching reap record follows actual waitpid. Use no-follow opens, regular owner-owned mode-0600 single-link files, bounded record counts and size, and a closed schema. The executor requires the exact expected helper roster, matched spawn/reap pairs, consistent identities and successful cleanup before accepting an otherwise passing native report. Missing, duplicate, foreign, malformed, out-of-order or oversized evidence fails closed.

On executor timeout or application crash, terminate/reap only its owned direct application. Closing inherited leases causes helpers to exit. Observe journal-known identities until absent or a different start identity proves the original exited; do not treat proc_pidpath failure, a zombie or a denied query as absence and do not signal an unverified/reused PID. A spawn-before-journal crash gap cannot produce a successful cleanup claim: preserve evidence, fail qualification and wait the helper's maximum lifetime before bounded recovery. No blanket process kill or fixture deletion is permitted on unverified cleanup.

## Failure verification and evidence

Before the full native run, prove readiness timeout, malformed arguments/channels, ignored SIGTERM followed by verified kill, normal lease EOF, absolute lifetime, actual parent death, nested fork denial and descriptor noninheritance. Distinguish direct-child waitpid receipts from orphan disappearance observations. Exercise missing/duplicate/wrong-identity journal records and malformed report schemas without running real repositories. Retain failed evidence; retries are new attempts and cannot erase failures.

Run the complete closed M5 roster, including combined UI and all three latency trials, against exact source and binary hashes. Record expected/executed case IDs, subprocess outcomes, cleanup disposition and sandbox identity. No skipped/missing case may satisfy the aggregate. Other native entrypoints remain separately inventoried and qualified; this component alone does not establish all application CI.

## Documentation and delivery

Restore the dirty-after-selection scenario in the repository README and native acceptance runbook through a doc-warden transaction. It is a disposable-fixture compatibility scenario, not a claim that historical screens or scripts are current or accepted. Runtime source checks must verify its real taxonomy rather than adding meaningless prose only to satisfy a string assertion.

Implementation uses a private candidate until the existing source-publication gates pass. Independently review the implementation and executor, build testing and production configurations, verify helper-route exclusion from production, and retain exact receipts. Merge only through the approved repository route. Rollback is a reviewed source revert or an unpublished candidate correction; installed applications and user data are untouched.

## Platform evidence

Descriptor actions follow [Apple's posix_spawn file-action contract](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/posix_spawn_file_actions_addopen.3.html). Confirm CLOEXEC-default and group flags against the selected macOS SDK headers at build time. Process start identity uses [Apple's proc information implementation](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.c); preserve the exact local SDK and executor source hashes in qualification receipts. A later hosted image/toolchain requires its own evidence.
