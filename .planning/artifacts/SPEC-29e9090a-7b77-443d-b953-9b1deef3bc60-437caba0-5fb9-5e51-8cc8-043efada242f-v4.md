# Retained command custody, installation transaction and bounded cleanup

Version 4 preserves the version 3 body below and adds the final installation amendment under ADR 0009. That amendment prospectively controls only the explicitly named installation scopes and lock-order exception. All other requirements and deadlines remain. This is a design contract; implementation, complete CI, signed-byte qualification, installation and physical acceptance remain separate gates.

# Retained command custody and bounded cleanup

## Authority and adoption boundary

This is the prospective version-2 successor to `SPEC-29e9090a-7b77-443d-b953-9b1deef3bc60-81b2dc00-4f47-5a79-be4c-519eea5ce71f` version 1, SHA-256 `9d89b615de8a2fc6262d3d9c895f3e7f4dec8b558feb556bc8ad33ee9bce7b65`. The predecessor remains immutable. Its direct-child ownership, identity, testing, scope and release restrictions continue except for the explicit non-reaping terminal-anchor extension below. This successor resolves OWNER-03's required protocol design and specifies the remaining OWNER-02 integration and OWNER-04 qualification; adoption does not establish their implementation or completion.

Approved PRD v3 REQ-SF-05 owns process custody. REQ-SF-04/08 retain policy-before-access and publisher-resource qualification; REQ-MG-03/06 retain one effective operation authority, staged readiness and safe recovery; REQ-GV-06/07/08/11 govern discovery, sharding, exact evidence and documentation. PLAN v3 remains the parent execution authority. No controller deployment, fleet rebinding, installed activation, new updater, privilege escalation, launch-on-login change, OS expansion or UI redesign is added.

The historical v2 adoption candidate had 199 source files. Component evidence establishes the shared direct-child owner, worker-owner integration and lifecycle caller conversion; the latest component run executed 54 M1/M4 cases, 267 tooling tests and 120 production-exclusion checks. Those observations do not qualify the new protocol, all current suites, installed system commands, signing, migration, updates or UAT. These extend the coverage inventory; they are not newly observed live PID-reuse incidents and do not alter the predecessor's original audit count.

## Selected process topology and trust boundary

Use one short-lived command custodian per external command transaction. It is a production dispatch role of the signed ShadowSync executable, `--shadow-sync-command-custodian`, entered before AppKit initialization. It is not a launchd service, a new installation authority, a shell, a generic RPC executor or a privileged daemon. Bare invocation refuses before candidate access. Production obtains the executable only from the verified release bundle; development fixture entry is compiled out of production. The lifecycle coordinator may launch the role from its already verified transaction bundle under the existing installation specification; arbitrary alternate app paths cannot select it.

The caller is the custodian's direct parent and exclusive reaper. The custodian is the actual command's direct parent and exclusive reaper. Both have separate isolated process groups. The actual command is leader of its own group, separate from the worker, app and custodian. Git preflights execute serially as custodian-owned command groups; no nested trampoline launches another custodian. The custodian remains alive through preflight, execution, drainage and terminal receipt publication.

Caller cancellation uses the inherited control channel. Once target admission is possible, the caller must not KILL the custodian to meet a timeout. Killing an admitted custodian would destroy the child anchor. Worker TERM/KILL does not reach the separate custodian group. When the worker dies, the custodian observes EOF on a pipe whose sole writer belonged to that worker, stops new admissions, and drains its own command groups. App-side post-worker-loss code observes journals and lock convergence; it never adopts or signals a recorded command PID/group.

This is authority against accidental races and failures in cooperating application processes, not a security boundary against arbitrary same-user code or a kernel adversary. Process identities and journal nonces are bindings, not passwords or transferable signal capabilities. Direct-child ownership, inherited descriptors and publisher verification supply the actual authority.

## Closed protocol, admission and descriptors

Use length-prefixed canonical UTF-8 JSON over inherited descriptors, with duplicate keys, unknown fields, invalid enums, trailing bytes, oversized frames and unexpected sequencing rejected. Each control/status frame is at most 16 KiB; one sealed request is at most 1 MiB. Output remains separate byte streams with the caller's existing smaller bounds, never an unbounded JSON field. No shell interpolation or PATH resolution is introduced.

`shadow-sync-custody-request/v1` binds request UUID, scope UUID, nonce, caller generation, trusted UID, boot session UUID, source/release-contract digest, typed command kind, approved arguments/environment representation, monotonic absolute work/TERM/KILL deadlines, output bounds, and descriptor roles with fstat identities. Candidate paths and opaque policy input occur only in the sealed request/input descriptor, never helper argv, environment, journal, diagnostic or control frame. Actual tool argv retains only the existing command-specific allowed arguments; policy candidates remain on the policy helper's stdin. The custodian reconstructs arguments/environment from a closed command-kind adapter and re-runs existing validators. The request cannot grant arbitrary executable, signal, filesystem or cleanup authority.

Production kinds are `repository-git`, `discovery-git`, `system-git-config`, `github-read-only`, `policy-classify`, `retention-archive`, `awa-removal`, `launchctl-read`, `launchctl-mutation`, and `signature-check`. Each kind has a fixed executable or separately publisher-qualified executable, existing allowlisted arguments, maximum input/output, authority mode, permitted resource descriptors, and fixed working-directory binding. No generic kind or command fallback is permitted. Changes to a kind's capability require a reviewed successor. The implementation's command-kind table and source-contract tests must enumerate all routes.

Use FD 190 for the sealed read-only request, 191 for caller-to-custodian control/liveness, 192 for custodian status, 193 for the verified state-directory descriptor, 194 for the retained log-namespace lease, 195/196 for existing frozen Git config descriptors when relevant, 197 for lifecycle lease, 198 for operation lease when the mode requires it, and 199 for run lease when present. Command-specific input/code descriptors remain explicit (including policy input and code FD 9); normalize collisions before posix_spawn. Validate access mode, regular/directory/pipe type, device/inode, ownership, link and ACL constraints as appropriate. A mode cannot pretend an absent operation/run descriptor is present. The launch manifest is closed and includes every inheritable descriptor. All other descriptors have CLOEXEC; no target or unrelated helper inherits a caller liveness writer or custodian control/status/state-directory descriptor.

Target commands may inherit only their declared standard streams, required read-only resource descriptors, and the operation lease where present. The custodian retains the full lease set and resource snapshots. Inheriting the operation descriptor provides additional exclusion if the custodian crashes; target code can close it, so the durable journal is also mandatory. Never issue LOCK_UN on a duplicate descriptor, reopen a lock to simulate transfer, or replace a lock inode.

Admission sequence:

1. Under an existing authority scope, the caller seals the request, records `prepared` durably, and reserves its cleanup-registry entry before spawning. No target is admitted yet.
2. Spawn the custodian suspended with the closed descriptor manifest. Successful posix_spawn immediately creates an exclusive spawn anchor, before fallible identity capture. Validate direct parent, UID, start identity, isolated group, executable publisher and release. Only then resume the custodian. A bootstrap failure is cleaned through that same anchor; no Foundation reaper or detached wait competes with it.
3. The custodian validates its own release, account, request, descriptors and scope, reconstructs the command adapter, and sends `ready` bound to the nonce. It has still created no target child.
4. The caller revalidates its scope and sends exactly one `admit`; cancellation, invalid control or EOF wins over admission. The custodian atomically writes/fsyncs `admitted` before spawning any target. It may not spawn after its work deadline.
5. Each actual target is spawned suspended into its own group and immediately anchored. Revalidate resource snapshots, current policy where applicable, executable publisher and suspended dynamic-code identity. Policy interpreter validation runs in the custodian using Security APIs and the retained publisher resources, not a serialized closure or a pathname assertion. Persist `executing` and target observation before SIGCONT. After all validation and durable writes, the single custodian event loop drains already available control frames/EOF without blocking and enters one final resume transition shared with cancellation. It rechecks the absolute deadline, scope admission and every observed cancellation/EOF/protocol fault immediately before the owner sends SIGCONT. An expired or cancelled transition drains the still-suspended child without executing target code. The linearization point is that final local transition: it does not promise instantaneous knowledge of a caller death or control byte that has not reached the custodian. Cancellation arriving after resume triggers ordinary owned drainage. A lost control channel cannot re-open admission. Refusal drains the suspended child without executing target code.
6. Complete bounded I/O, target/group drainage and exact reaping. Persist/fsync a terminal receipt before releasing authority. Send status, close descriptors, then exit. Failure to persist terminal state never becomes a successful command result.

Initial positive-PID bootstrap signaling is permitted only for the direct child returned by this successful suspended spawn, while an exclusive unreaped spawn anchor exists and the process has never been resumed. It permits SIGKILL only, never group signaling, and shares the owner mutex with nonblocking waits. Identity capture failure therefore cannot strand a child or justify a borrowed-PID kill. After resume, the verified direct-child/group contract applies. ECHILD always poisons custody.

## Authority scopes, pre-policy work and staged readiness

Introduce a typed `CommandCustodyContext`; neither a path nor a bare FD constructs one. Contexts own or duplicate authority already held in the documented order: log namespace, lifecycle, operation, optional run. An existing run/lifecycle mutation passes duplicates of its actual descriptors. It never recursively acquires a separate flock or upgrades shared locks. The registry tracks a context's unique scope UUID and open/closing/pending/terminal state; cancellation or unresolved cleanup closes that scope to new commands.

A standalone policy/discovery/read-only GitHub phase acquires a read scope: namespace SH, lifecycle SH, operation SH, no run lock. Only app-owned state is touched to establish it, before candidate classification; a lease is not permission to access a candidate. Scope creation checks durable custody under those locks. All commands in that phase borrow that same context. A concurrent mutation needing operation EX reports existing busy behavior and keeps its prior inventory; it does not reinterpret contention as an empty inventory. Before converting a read phase into mutation, drain its commands, close the read scope, then acquire fresh operation EX and repeat required preflight. There is no lock upgrade or check-to-mutation authority transfer.

`launchctl-read` and `signature-check` also support a narrow lifecycle-observation scope: namespace SH and lifecycle SH, no operation/run lock. It is restricted to the fixed service label and canonical or coordinator-verified app bundle and cannot classify, enumerate, read or operate on repositories. It permits staged host identity/readiness while the coordinator retains operation EX. If the caller already holds lifecycle authority, borrow it; never recursively obtain a conflicting lifecycle lock. The observation custodian keeps lifecycle exclusion until drainage, so app replacement cannot race verification. Bootstrap trust is verified with in-process Security APIs to avoid recursively invoking signature-check. `launchctl-mutation` requires the coordinator's lifecycle-mutation context and operation EX. Readiness cannot start repository work or acquire an operation lease it was not given.

Journal writes are per-transaction, with one writer: caller owns the initial prepared record, then custody ownership is transferred to the verified helper by the closed admission handshake. Caller reaping is recorded in a separate observation receipt. The mandatory catalog described below independently records the expected transaction set. Its stable metadata guard is acquired last and held only across bounded metadata transitions; it grants no operation permission. No shared append file, replacement operation lock, or inode-replacing lock protocol is introduced. Mutation admission obtains the existing exclusive locks and checks every relevant journal before candidate access. A valid terminal journal needs no process signaling; a pending/unknown record outside the explicitly borrowed live scope blocks new repository work. Observation-only diagnostics remain possible but cannot clear that fence. In-flight records within one live scope are permitted only through its in-memory typed context, not by copying its UUID from disk.

## Bounded waits and retained ownership

Every request uses one absolute monotonic timeline in the boot's monotonic clock domain. The caller computes it once; nested preflights, IPC waits, output polling and cleanup consume it without resetting the work budget. Reject non-finite, negative, overflowed, reversed, stale-boot or out-of-policy values. Preserve existing command work timeouts (including the policy helper's two-second work bound and lifecycle commands' ten seconds). TERM grace is at most two seconds and the initial post-KILL observation window at most two more seconds, included explicitly in the total transaction budget. Caller-side receipt/exit allowance is at most one further second. Existing shorter caller budgets continue to win. Tests may use only the existing compile-time budget scaling contract and record the actual limits.

At cancellation, EOF, malformed control, output overflow or work expiry, close admission and send TERM through the custodian's actual direct-child owner. Continue bounded I/O. At TERM deadline send KILL through that owner. At KILL-observation expiry return `cleanup-pending`, never `succeeded`, `cancelled-complete`, `childReleased`, `no-service`, or a zero exit. The custodian remains the responsible cleanup process, retaining its anchors, full authority, resource snapshots and journal; it polls nonblocking at a bounded low rate until terminal convergence. It does not repeatedly signal on every poll or create an unowned background thread. Its continued existence is not a reason to hold the caller/UI synchronously forever.

The caller's process-lifetime `RetainedCleanupRegistry` retains the custodian anchor, pipe readers, scope and resource references after a bounded API returns pending. Registry ownership is acquired before any spawn; partial construction and throw paths cannot bypass it. One serialized timer/event loop polls actual anchors and drains bounded status/output. Entries retire only after terminal evidence and actual custodian reaping, or explicit durable recovery. Normal quit may transfer responsibility to an already admitted custodian and close the exclusive liveness writer; it must not kill that custodian or report its operation complete. If the caller itself dies, the custodian continues independently and is eventually reaped by the OS after it exits; a successor app observes the terminal journal and lock convergence rather than falsely claiming it reaped a non-child.

## Terminal anchors and descendant drainage

An exited group leader must not be reaped while its remaining group still requires signaling. Extend the shared owner with an explicit terminal-held state and `waitid(P_PID, exactPID, ..., WEXITED|WNOHANG|WNOWAIT)` observation under the same mutex. Zero-initialize siginfo, treat si_pid zero as no result, require exact PID and supported terminal codes, and treat ECHILD/unexpected results as ownership failure. No unrelated caller may reap the anchor. Once terminal-held is proven, the immutable adopted group binding and still-unreaped anchor permit group cleanup under that mutex even when executable-path queries cease to work for a zombie; this does not authorize signals after final reap or ownership failure.

The custodian admits only qualified fixed-tool execution graphs with a non-detaching behavior contract under their exact closed environment/configuration. This is an explicit execution-adapter assumption, not something proved by process-group enumeration. Existing hook, credential-helper, pager, filter, transport and executable restrictions remain. Each production kind must have a reviewed graph and prohibited escape-capable options/configuration, bind the qualified executable identities in its release evidence, and refuse an unknown/unqualified executable or graph before spawn. An optional adapter such as gh remains unavailable until qualified. An operating-system/tool update outside the qualified identities triggers requalification, not trust from its pathname. The requirement is bounded cleanup for these admitted cooperating commands; no guarantee is made for arbitrary injected code that deliberately detaches and closes inherited descriptors. Relaxing that assumption requires a stronger kernel mechanism and a successor decision, not a test waiver.

A complete bounded kernel process-group enumeration must show exactly the retained terminal leader and no other members before final reap. Require a successful API result, the leader present, byte/count units converted correctly, and no full/truncated buffer; use an oversized buffer with a fixed 4,096-PID ceiling and at most three allocation/retry passes. The public proc_listpids wrapper can return zero on failure, so zero/absent leader is never clean. Keep the anchor while inspecting; reject inconsistent observations and retry only within the cleanup budget. Require output EOF for all intended streams and drain completion separately. Then perform the one exact waitpid reap, record raw status and refuse every later signal. No borrowed descendant PID is signaled. These observations establish convergence only under the qualified non-detaching graph assumption, not ancestry or universal descendant containment.

The implementation must qualify this anchor/enumeration behavior on supported macOS 26, including a leader that exits while a TERM-resistant descendant remains. The exact wrapper and every kind's graph are CUST-01/CUST-03 review gates before that kind is enabled. An observed escape, lost anchor or inaccessible evidence poisons the transaction and retains the fence. An unobserved closed-stream escape cannot be detected by group/EOF checks; do not claim otherwise. The qualification harness independently observes a fixture that setsid/setpgid and closes stdout/stderr, demonstrates this limitation, and rejects that graph's registration even if the ordinary group/EOF observations appear clean. Its independent fixture owner cleans it safely. Public production registration must reject the corresponding escape-capable route before admission. Actual fixed-tool graph qualification must use its permitted arguments/configuration and include worker death at its descendant-producing phases. If any required existing route cannot establish the non-detaching contract, that route and installed rollout stay blocked until a reviewed platform solution exists. No observed qualification failure may be converted into successful cleanup or silently excluded from the roster.

## Durable state and recovery

Use owner-private `custody/<request UUID>.json` beneath the verified existing state-directory descriptor. Each record is a no-follow, single-link regular file, mode 0600, at most 32 KiB; the custody directory is 0700. Atomic same-directory writes, file fsync and directory fsync precede consequential transitions. Reject conflicting UUIDs, unexpected hardlinks/symlinks, wrong ownership/mode, unknown/newer schema and malformed data. Preserve evidence; do not reset it. State migration moves this directory with the same namespace and lock inodes, and may not begin while any custody is unresolved.

A mandatory `custody/catalog.json` (schema `shadow-sync-custody-catalog/v1`) independently lists all outstanding request IDs, scope/kind/authority mode, boot/release binding, and expected journal filename. It also contains a fixed initialized-format marker and increasing revision. Absence is an error even when the directory is otherwise empty. Only the signed fresh-install initializer for verified new state, or the accepted identity-migration transaction for validated legacy state, creates an initialized empty catalog. Ordinary startup and command code cannot recreate a missing catalog or reinterpret old/new state as fresh. Fixtures use an explicit isolated initializer.

`custody/catalog.lock` is a stable owner-private metadata-serialization file, created by that same initializer, never unlinked/recreated or used as operation authority. Acquire its EX lock last, after the applicable namespace/lifecycle/operation/run leases; never acquire a higher-order lock while holding it. Release it before spawning, waiting, callbacks, target I/O or resource validation. Catalog writes use atomic same-directory replacement and directory fsync while the distinct guard inode remains stable. All caller/helper writers use this order. Missing/contended/invalid guard fails closed; a bounded contention result does not reset evidence.

For every new command, under one catalog-guard-protected transition, reconcile the mandatory catalog with journals/archived receipts, evaluate the mode-specific fence, and reserve its outstanding entry. Repository/policy and mutation modes reject unresolved outside-scope transactions. A valid fixed lifecycle-observation mode may coexist with a known pending transaction solely for diagnostics/readiness; it cannot access repositories, mutate registrations, clear the fence, or treat malformed/missing catalog evidence as valid. Recheck at each reservation; a scope-construction check is not cached admission. This includes concurrent read scopes and prevents two empty-catalog observations from admitting conflicting scopes. Fsync the reserved entry before publishing the prepared journal, and publish/fsync prepared before helper launch. A crash between these steps leaves a known missing journal and blocks work. The catalog records identity/expectation, not each mutable journal digest, avoiding a two-file state-transition atomicity claim. A validated terminal receipt is archived with a digest and fsynced under the existing retention rules before outstanding registration can be removed. Remove the registration atomically/fsync before retiring the corresponding terminal journal; interruption leaves either a conservatively outstanding valid terminal record or an extra terminal journal that can be matched to its archived receipt. Unknown extra/nonterminal journals block admission. No transaction is forgotten because its helper exited. At most 128 outstanding entries are allowed; overflow returns busy without launching, deleting or replacing an entry. Mandatory catalog and guard presence remains after the last entry retires. Retained terminal receipts follow the existing recovery retention gates.

`shadow-sync-custody/v1` contains only schema, transaction/scope IDs, nonce digest, boot UUID, release-contract digest, command kind/authority mode, monotonic deadlines, process identity observations, lease device/inode bindings, transition ordinal, phase, bounded closed result/reason codes, wait status and input/resource digests. Never persist candidate paths, args/environment, policy payloads, stdout/stderr or secrets. Phases are `prepared`, `admitted`, `executing`, `draining`, `cleanup-pending`, `terminal`, and `recovered-after-boot`. Terminal outcome separately distinguishes completed, command-failed, admission-refused, cancelled-drained and timed-out-drained. Pending is never terminal. Retain the last known complete preimage when a replacement fails; atomicity is not a guarantee against same-user corruption.

Recovery rules:

- Caller/worker loss: liveness EOF automatically triggers custodian drainage. A surviving app waits only to its response deadline, presents unresolved status if needed, and continues observing. It must not call the old borrowed `drainRecordedChildAfterWorkerLoss` signal path.
- Interrupted setup or prepared journal: the spawn owner can publish admission-refused only after proving no target ever admitted and reaping its own helper (or posix_spawn returned failure). A different process cannot infer this from a prepared record or absent PID; a delayed helper could still exist.
- Custodian loss: preserve the nonterminal journal and all surviving inherited leases. Same-boot successors may inspect but cannot signal or adopt orphan identities or clear the fence merely because locks/PIDs appear absent. This separate failure does not replace automatic worker-loss drainage with manual cleanup.
- Prior-boot valid journal: read `kern.bootsessionuuid` directly, require a valid different boot UUID and fresh exclusive original namespace/lifecycle/operation authority, preserve the journal and affected operation's existing pre/postflight evidence, and record `recovered-after-boot` as interrupted/unknown operation result. Never call it successful, rerun a mutation automatically, or infer unchanged Git refs. Reconcile/revalidate repository state through the existing policy-gated recovery path before any new operation. No automatic reboot is authorized. Missing/unqualified boot identity fails closed; wall time, app version and PID absence are not substitutes.
- Missing, malformed or conflicting records and unknown newer formats remain a data-preserving refusal. A signed recovery procedure requires a verified journal/preimage or a separately reviewed repair; ordinary startup cannot delete the evidence. Loss of a known expected record is not absence of a transaction.
- Failed replacement, Sparkle, install/migration or rollback: unresolved custody blocks replacement and namespace moves. The existing coordinator remains the only installation authority. Staged readiness may use only the observation scope above, with no repository access. A post-reap/postflight failure is a failure receipt, not permission to revert recognized user data.

## Discovery resource ownership successor

This version changes only discovery's resource preparation and retirement within CUST-03. The predecessor remains frozen evidence. Its process topology, authority modes, closed command roster, original deadlines, policy/publisher checks, Git safety, cleanup fencing and external completion gates remain required. This is design authority only; it does not qualify a production caller or a tool graph.

The production caller cannot supply a frozen configuration before its sources have been policy-approved. Calling the separate system-configuration probe first, or allowing snapshot helpers to repeat it, would split discovery's preflights across custodians and reset their work budget. Therefore one discovery custodian derives, creates and retains its own frozen configuration and execution snapshot after serial policy admission. The caller retains the same live phase and publisher capability through completion or registry-owned pending work.

### Closed request and admission

`shadow-sync-discovery-custody/v2` replaces discovery's unpublished v1 input contract. It carries only the current policy identity commitment and one selected primary repository's exact path, expected physical repository/root metadata and origin identity required by existing discovery validation. These are integrity claims, not access authority. Strict canonical/duplicate-key/size validation, exact selected-scope binding, current-account checks and the existing command allowlist remain mandatory. It accepts no caller-selected scratch location, frozen snapshot, executable or additional configuration. Discovery v1 input and extra inherited frozen descriptors are refused on the production v2 route; legacy fixtures remain explicitly testing-only. Other command input formats are unchanged.

The caller allocates one original absolute command budget before command rebinding and creates one sealed request under the same retained authority. A phase-owned typed adapter supplies the actual context, publisher resources, binder and cancellation. It must not reconstruct those capabilities from saved metadata or extend the callback's lifetime. Metadata-blocked candidates return their existing blocked presentation without Git. Eligible candidates retain the existing origin, transport, worktree, reference and cleanliness inspection semantics. Unsupported linked resources remain refused until their existing required admission is implemented; no relaxed fallback is introduced.

The helper first validates the current publisher, policy commitment, selected binding and qualified fixed-tool graphs without touching the candidate. It runs system-configuration discovery, observes complete bounded streams and actual reaping, then performs every policy-classification batch serially. Every stage consumes the original budget. Resource paths include the exact existing repository metadata roster, derived user/system configuration sources, and the future transaction-owned frozen directory/file, with all ancestors classified before traversal or creation. A denied, malformed, expired or interrupted batch prevents subsequent resource access, freezing and final Git.

### Transaction-owned frozen resource

Derive the future directory lexically from the existing request UUID beneath the fixed private temporary-resource namespace; the request cannot choose its path. The deterministic UUID-based name is distinct from the historical six-character snapshot names. Classify that exact destination and ancestors before creation. Validate the temporary-root descriptor and use exclusive no-follow creation with owner-private modes; any existing entry, symlink, hardlink, unexpected owner/ACL or name mismatch refuses without adopting, overwriting or removing it. Never enumerate sibling snapshot directories or call the broad stale-snapshot recovery routine on this path.

After policy admission, the helper opens and revalidates the exact selected primary repository, captures only the completed preflight's configuration sources, rejects includes and existing unsafe configuration, then freezes the same bounded immutable bytes used by current Git safety. New captured-preflight overloads perform no subprocess invocation: an absent system source stays explicit and cannot invoke a legacy probe. Create the execution snapshot from the same retained repository and frozen resources; validate it immediately before target resume and in postflight. The snapshot's frozen owner is this actual helper, not the caller. Recheck policy, current phase/control state and original deadline after resource work and before any target resume.

FDs 195/196 are absent from the caller-to-helper discovery v2 manifest. The helper retains its created directory/file descriptors and maps only the read-only frozen file to target FD 196. The existing operation lease and declared streams remain the only other target resources; temporary directory, control/status and caller liveness descriptors do not leak. Other commands' existing inherited frozen-resource roles remain unchanged. Targets still use the closed frozen-config environment and exact qualified Git graph.

### Cleanup, persistence and recovery

Explicit resource retirement is part of transaction completion. Before creating a scratch directory, durably bind its deterministic request identity and creation intent beneath the existing custody fence. Record each successfully acquired directory/file identity and creation phase in a bounded, strict, owner-private resource receipt before admitting a Git target. The receipt contains only transaction/boot/release bindings, creation/cleanup phases, file identities, content digest and size; no candidate paths, configuration bytes, arguments or output. Use a versioned closed schema and existing atomic replacement/fsync discipline. Missing, malformed, newer or conflicting resource evidence fails closed. Creation failure between steps remains nonterminal until the creating helper proves cleanup of exactly what it created.

Keep the helper's resource owner and original leases alive through child drainage, postflight and cleanup. Successful return, command failure, cancellation and timeout all require exact-child/group retirement, stream EOF and verified identity-bound deletion of this transaction's frozen file and directory. Do not rely on a throwing destructor whose error is suppressed. Partial cleanup is idempotent under the retained descriptors and recorded phases; do not require a removed file to be present on retry, interpret a replacement as the original, or perform broad cleanup. Cleanup failure returns/retains `cleanup-pending`, closes admission, persists the fence and cannot publish terminal success. Cleanup observes the existing bounded response allowance and retains ownership for later convergence.

Worker loss is handled by the already admitted helper using its existing liveness channel. Helper loss preserves the same-boot fence and resource evidence; another process cannot infer safe deletion or success from absent PIDs/locks. Prior-boot or separately authorized signed recovery uses the existing exclusive recovery authority, the deterministic request location and verified persisted identities; ambiguity preserves data and requires repair. No automatic reboot, broad orphan sweep, old-software launch, lock inode replacement or user-data deletion is added.

Application engineering owns the caller/adapter, helper preparation and transaction resource owner; release engineering owns suite inventory and exact-source receipt coverage. Independent source and evidence review remains required before integration. Preserve v1 evidence and the qualified predecessor candidate; no prior-source pass counts toward the changed contract.

# Bounded installation transaction and staged-readiness contract

## Authority and narrow supersession

ADR-0003, Transaction invariants (lines 31–42), requires an fsynced installation transaction before consequential mutation, continuous operation authority, staged readiness without repository/network work, and recoverability. Its Admission-safe migration order steps 2, 4–6 (lines 51–55), and Recovery (lines 81–83) require original lock identities and stopped precommit restoration. ADR-0008 lines 26–32 and 50 retain those requirements, the signed coordinator and explicit startup opt-in; the reachable defect here is that command journals cannot fence command-free installation gaps and the current staged boolean permits full startup.

This decision adds one separately typed installation control and one coordinator-owned staged readiness capability. It prospectively amends custody SPEC v3 “Authority scopes, pre-policy work and staged readiness” lines 51–57 and “Durable state and recovery” lines 83–101 only for the closed installation modes below. The fixed command-kind roster, inherited descriptor roles, target custody, direct-child signaling, original deadlines, pending semantics and other admission rules remain unchanged. Observation never acquires mutation rights.

The sole lock-order exception is the bounded nonblocking reacquisition of existing admission inodes while a uniquely retained original operation EX description stays held, as specified below. For namespace-moving rollback this expressly supersedes ADR-0003 step 2's no-lower-order-lock rule only at the rollback reentry described here; initial migration still follows that rule. No other lock upgrade, unlock, new lock inode, or operation-description reopening is authorized.

## Mandatory control and exact storage shape

Use `custody/installation.json`, schema `shadow-sync-installation-control/v1`, a canonical UTF-8 JSON object of at most 32 KiB. Reject duplicate/unknown fields, noncanonical encoding, trailing bytes, invalid enums, integer overflow, and invalid field combinations. It is owner-private, no-follow, regular, single-link, mode 0600. It is mandatory alongside catalog.json, catalog.lock and receipts. It is not a command journal, fake launchctl command, catalog command entry, or replaceable lock.

Extend the current CustodyCatalogStore with typed installation read/transition methods using its existing `locked`, bounded `read`, and exact-preimage `write`. `snapshot` explicitly recognizes this one filename and validates it under the same catalog.lock; all other unexpected files still refuse. The guard stays last and is released before code verification, lock acquisition, callbacks, command launch or IPC. Command reservation checks installation state and command custody within that single guard interval. Never nest another catalog guard acquisition.

Top-level fields are exactly:

| Field | Closed value / constraint |
| --- | --- |
| schema | Literal above. |
| revision | UInt64, starts at 1, checked increment on every replacement. |
| phase | `initial`, `active`, `committed`, `recovery`. |
| state | Existing state directory device/inode/uid, plus stable lock identities for namespace/latest.log, lifecycle, operation, run, launcher and catalog guard. Fixed keys; node identity/mode/link/ACL validation remains mandatory. |
| transaction | Null only for initial; otherwise the transaction object below. |
| step | Null for initial; otherwise one fixed action intent/completion below. |
| latestReceiptDigest | Null only for initial; otherwise SHA256 of the exact latest complete durable step receipt. |
| readinessCommit | Null until irreversible readiness commit; afterwards the exact commit receipt below, never erased in recovery. |
| recoveryReason | Null except recovery; one of `interrupted`, `command-pending`, `persistence`, `identity-conflict`, `readiness-failed`, `cleanup-failed`, `startup-uncertain`, `restored-stopped`. |

`transaction` has exactly `id` (UUID), `boot` (direct kernel boot UUID), `intent` (`install`, `repair`, `migrate`, `remove`), `coordinator` (PID/start identity/generation and expected helper team/identifier/CDHash), `sourceReleaseDigest`, `candidate` (exact ReleaseIdentity, canonical bundle SHA256, app CDHash, coordinator CDHash; null only for removal), `priorCommitDigest` (null for fresh state), and `slots`. PID/generation and disk bytes bind evidence; they do not authenticate a caller. Code identities derive from verified release resources, never untrusted strings.

`slots` is a fixed-key map for existing installer slots: current application, predecessor application, application incoming/incomplete, application previous, predecessor previous, launch plist, plist incoming/incomplete/previous, state namespace source/destination, host owner/socket and their existing previous slots, plus the distinct coordinator readiness socket installation.sock. Its creation and retirement have their own exact pre/postimages in open-staged-admission and cleanup receipts. Unknown orphan endpoints remain fenced; PID absence, pathname presence, or ECONNREFUSED alone never authorizes deletion. A legacy previous-name alias is accepted only by its existing token-specific compatibility reader. Each slot is `absent` or `present` with retained parent device/inode, node device/inode/type/uid/mode/link and ACL digest, size where meaningful, and content/bundle digest for regular data or sealed bundles. Socket identity has no content digest. No arbitrary path, shell command, repository name, args, environment, output, or policy data is stored. Fixed slot enums resolve through InstallationPaths and the existing installer layout. State document translation uses the already accepted fixed document names and durable preimage receipts; its slot evidence must reference their exact receipt digests. If a reachable route cannot supply that evidence, it refuses rather than omitting a document or inventing an empty preimage.

`step` has exactly `ordinal` (checked UInt64), `action`, `status` (`intent`, `complete`), `preimageDigest`, and `postimageDigest` (null only for intent). `action` is one of `reserve`, `drain-prior`, `stage-application`, `stage-plist`, `retire-application`, `retire-plist`, `retire-coordination`, `translate-state`, `move-state-forward`, `promote-application`, `promote-plist`, `open-staged-admission`, `bootstrap-candidate`, `kickstart-candidate`, `candidate-ready`, `readiness-commit`, `cleanup-coordination`, `cleanup-backups`, `cleanup-incoming`, `candidate-stop`, `move-state-back`, `restore-application`, `restore-plist`, `restore-coordination`, `remove-installation`, `finish`. The implementation enumerates a closed transition table per intent, including its recovery branches, and rejects an action not in that table before its durable intent or filesystem action. No caller-provided action list is executable. The fixed intent selects a finite legal action sequence; absent slots produce an evidenced no-op completion, not a filesystem action. Exact pre/postimage digests bind the corresponding full fixed-slot snapshots retained in the transaction's durable receipt chain. Persist the intent plus preimage evidence BEFORE each action. After the action and its affected-directory fsync, revalidate exact postimages and persist completion. An intent on recovery means “action may have occurred,” never success; reconcile only its exact before/after layout, refuse any third state. Never repeat bootstrap/kickstart because their step is incomplete.

Receipts use the existing owner-private receipts directory with a separately recognized fixed installation receipt prefix, bounded canonical records and exact digest chaining, not UUID command archives. Every receipt has schema `shadow-sync-installation-step/v1`, transaction ID, ordinal, previous receipt SHA256 (null first), action/status, complete pre/post slot snapshots and the same state/release binding. The control references the latest durable receipt digest. Publish/fsync receipt first, then atomically replace/fsync control. A cut leaves either the old complete control or a known unreferenced receipt; reconciliation accepts only the exact next ordinal/digest/preimage continuation under coordinator authority, never arbitrary extra evidence. Limit a transaction to 128 steps; overflow refuses before mutation. Retain unresolved evidence. This is a concrete installation journal fulfilling ADR-0003; it cannot be replaced by a bare phase field.

`readinessCommit` has exactly transaction ID, commit revision, candidate release/bundle/app/helper digests, state-binding digest, completed-step receipt digest, authenticated host PID/start/generation, and precommit transcript digest (hello, challenge, ready only). The completed-step receipt is the last candidate-ready completion, published before this commit; it contains no hash of the commit itself. It records convergence, not a reusable capability. `committed` requires it, except completed removal: removal remains a distinct fenced recovery/tombstone outcome and cannot admit an app. This bounded contract does not call removal an installed committed state.

For a committed installation, the transaction boot and coordinator process observations are historical evidence. Ordinary startup does not require that previous process to be alive or the machine to remain in that boot. A new transaction has a new live authenticated coordinator and current kernel boot binding; it cannot adopt an old process observation as authority.

Fresh initialization writes/fsyncs `initial` and its stable identity before ready/publication and includes it in initialized controls. Initial is fenced, not idle. Only authenticated coordinator begin moves initial or a fully validated committed installation to active. Recognized pre-control migration may create it under existing exclusive authority and preserved inodes. Ordinary startup cannot initialize, repair or migrate a missing control. Missing, malformed, newer, contradictory, or unsafe evidence means unavailable. Update fresh-publication receipts, strict state/custody allowlists and fixture initializers together.

Atomic updates retain the current catalog-store discipline: same-directory exclusive temporary, full write/file fsync, exact old bytes/inode/ACL preimage check, atomic swap/exclusive creation, directory fsync, then identity-bound obsolete-preimage unlink and directory fsync. Failed persistence preserves/poisons the fence; no catch converts uncertainty into committed or initial. New receipt filenames must be accounted for by the store's strict receipt enumeration, including interrupted creation. Reuse storage mechanics; do not expose a generic caller-selected path writer.

## Admission and transition table

| State / live authority | Permitted behavior |
| --- | --- |
| initial | Authenticated coordinator begin only; fixed diagnostic report. No host, repository, worker, policy, network, normal lifecycle or mutation admission. |
| active + exclusive installation owner | Fixed planned installer actions and custody-covered commands for this transaction; no ordinary operation. Record persists through command-free gaps and process death. |
| active + staged owner | Candidate-only start/stop/fixed diagnostics; readiness-only candidate host via authenticated session. No repository context. |
| committed + validated commit and exact allowed residual slots | Normal host startup may begin. Reads/runs/worker/policy still require their normal operation leases; coordinator retains original EX until cleanup/finish, so they remain blocked. No other transaction may start. |
| recovery, any reason | No ordinary entry. Original live owner may perform only its permitted drain/recovery actions; successor signed recovery must acquire its own standard-order exclusive recovery authority and reconcile evidence. A readinessCommit forces repair forward. |

Ordinary authority constructors, phase construction/revalidation, each command reservation, launcher/host admission, manual routing before activation/kickstart, installed verification, worker/run/recovery/inventory and app-owned consequential writes all check the mandatory control. A valid committed record does not bypass catalog/journal checks or residue validation. At commit the strict catalog must show every transaction command fully retired; a terminal journal or public `finished` snapshot alone is insufficient. Permitted backup/incoming residue is exact receipt-bound state, not an `allowStagedLifecycleResidue` boolean. A normal opener revalidates after acquiring its existing leases; no cached successful probe grants later access.

Fixed launchctl-read/signature diagnostics may report a VALID active/recovery transaction under the existing observation scope. They cannot clear the fence, construct repository-read authority, start a candidate, or treat malformed evidence as idle. If ordinary structured observation cannot open unsafe storage, an unavailable report remains possible without mutation.

## One-way owner transfer and bounded lock exception

Introduce an internal consumed InstallationTransactionOwner that alone owns the original operation EX description and pinned state. It is constructed only from authenticated LifecyclePublisher plus actual acquired/transferred authority. Generic RunAuthority acquisition cannot mint it from metadata. Before opening staged admission, permanently close every old command/observation/init borrow gate. On failure the gate stays closed. Require zero actual outstanding leases, prepared reservations and inherited copies; drain all owned custodian/target streams, terminal receipt fsync, direct-child reap and actual registry removal. RetainedCleanupRegistry.finish currently publishes finished before releaseChildCopies/remove; add an internal retirement barrier/result issued only after removal and resource release. Snapshot phase is never that proof.

Consume old owner once. Close the LAST original lifecycle and, where applicable, namespace/run/launcher admission descriptions after proving all aliases gone. Do not call LOCK_UN or convert SH↔EX. Keep the original operation description live continuously; never close/reopen or acquire a replacement operation description. Borrow counters alone are not sufficient unless all creation/init/handoff/registry/inherited aliases are structurally enrolled and checked.

Retain pinned state plus original namespace/lifecycle identity expectations; open existing same nodes descriptor-relative O_NOFOLLOW|O_CLOEXEC, no create or mode repair, checking named and descriptor identity, uid/mode/link/ACL before and after LOCK_NB. Acquire fresh namespace SH then lifecycle SH for staged readiness, no run. This intentionally reacquires higher-order locks while original operation EX is retained. It is allowed only in this consumed installation transition, with no catalog guard, registry callback or authority mutex held, within the existing deadline, using nonblocking attempts only. Contention or mismatch stops admission and preserves original operation/fence; close only newly acquired temporary descriptions. No ordinary blocking lock path may implement this exception.

Staged custody uses separately closed `installation-staged-start` and `installation-staged-stop` authority modes across request decoder, descriptors, journal, catalog, import, adapter and completion. Both carry state/namespace SH/lifecycle SH/original operation EX, no run, exact installation binding and parent capability. Start permits only fixed candidate bootstrap/kickstart plus fixed diagnostics. Stop permits only exact candidate lifecycle-exit/bootout plus fixed diagnostics. Existing command kinds remain; launchctl-mutation is extended only by this explicit reviewed mode. Generic bootout's ability to stop another release is not inherited. Stop cannot bootstrap/kickstart, restore, classify or operate on repositories. Borrowed observation never substitutes for either mode.

## Authenticated readiness over the existing socket/code-verifier seam

Use one narrow coordinator-owned `installation.sock` in the verified state directory, mode 0600, and a single persistent bounded session. Reuse HostControlIO's AF_UNIX/poll/deadline mechanics with a strict canonical decoder and add installation-specific messages; do not introduce a general RPC executor, daemon, XPC service or descriptor-passing framework. The listener is created only from the consumed staged owner; it does not accept generic callback-created authority. Endpoint cleanup is exact identity-bound; stale/unknown endpoints refuse unless signed recovery proves ownership and inactivity.

The managed candidate takes a distinct pre-AppKit branch. It may open only verified installation state, fixed candidate release resources and the readiness socket, and acquire namespace SH/lifecycle SH/launcher EX. It does not construct the normal delegate, menu/hotkey/recovery loader, normal activation server, repository context, worker, policy classifier, candidate inventory or network work. An active record alone does not admit even this branch: authentication below must complete before reporting ready. Failure/EOF exits this branch without normal startup.

Both endpoints obtain getpeereid AND LOCAL_PEERTOKEN (exact audit_token_t size) on the connected socket; LOCAL_PEERPID is a consistency check only. Reject unsupported peer-token/Security calls without falling back to PID lookup.

Messages are closed, at most the existing 16 KiB frame bound: `hello`, `challenge`, `ready`, `commit`, `normal-started`, `stop`, `stopped`; no arbitrary action/argv/path fields. Each binds transaction ID, boot, control revision, exact candidate release digest, state/lock binding digest, host generation, fresh session nonce and the expected previous message digest. Only one candidate peer/session is accepted; duplicates/reflected/reordered/stale messages fail closed. The transcript binds the session, not authority by itself.

On hello, coordinator revalidates live publisher, actual unique staged owner, original retained operation descriptor and all state/lock identities, open phase, record, current candidate and command retirement state, then issues challenge. Host independently validates its own running code/resources, peer coordinator exact code, active transaction and bindings, and returns ready. Coordinator validates the peer, fixed launchd program/PID convergence and exact candidate release again. Its response is issued only while that same typed owner still retains original operation EX. The host never receives an operation lease.

This is actual authority from a verified live signed coordinator whose code can issue the message only from the retained owner. There is no Darwin API here that proves arbitrary descriptors share one open-file description; fstat equality does NOT prove this. Continuity comes from move-only/consumed ownership, no reopen path, no unlocked alias, checked registry retirement and a closed descriptor manifest. A serialized UUID/PID/uid/lock-held claim cannot construct the endpoint or capability. The trust boundary remains the SPEC's cooperating signed processes, not arbitrary hostile same-user code.

Coordinator first retires every bootstrap/kickstart/diagnostic command, verifies exact app/state/plist/launch identity and permitted residue, then durably writes readinessCommit with phase committed. Only after file and directory fsync succeeds may it send commit on the authenticated session. Host rereads/validates the same committed receipt and exact transcript binding, then creates normal AppKit/delegate/control startup and responds normal-started. Original operation EX stays retained throughout, blocking repository/read/run work until cleanup and coordinator release. No message or in-memory boolean substitutes for durable commit.

EOF/timeout before host consumes a valid commit leaves host readiness-only and exits; it never infers commit. EOF after consumed commit does not roll back a committed host: subsequent startup/admission gates still apply. If coordinator cleanup fails after normal startup, first durably set recovery retaining readinessCommit, permanently close command starts, then request authenticated pause/exit and drain the exact host before repair-forward. Do not pretend writing recovery retroactively undid UI startup or released authority. If host cannot drain, retain original operation and recovery fence; do not restore old code. Same-process crash after commit also means repair forward, never precommit rollback.

The readiness listener must remain serviceable while a synchronous launchctl custody wait runs: use one bounded serial installation-session queue with no callback holding catalog/authority/registry locks, and send validated state changes back through an owner-serialized transition. It owns no operation duplicate. All deadlines consume existing caller budgets (including the current five-second readiness observation beginning after the existing kickstart path). ## Failure, rollback and successor recovery

Readiness/start failure first permanently closes start admission. Cancel/drain prior commands under retained custody; require terminal fsync, every intended EOF, exact reap, actual registry retirement and zero borrows before minting stop-only owner. Poisoned/ECHILD/pending/missing evidence blocks this transition and all restoration. Stop-only may cooperatively stop only the authenticated candidate and bootout only its exact fixed program/release. No best-effort swallowed error is stop proof.

Only after candidate host and command drainage, validated launchd inactivity, released host launcher/lifecycle admission, and retired stop commands may the owner close last staged lifecycle SH and freshly acquire existing SAME lifecycle inode EX while retaining namespace SH and original operation EX. For namespace-moving legacy rollback, close last namespace and lifecycle admission descriptions, freshly acquire original namespace inode EX then original lifecycle inode EX using the explicit bounded nonblocking exception, retain original operation EX, and acquire required run/launcher after it. No namespace parking/new lock creation; preserve the same state directory and lock identities across rename-back. Initial migration still acquires namespace EX from unheld state with no lower-order lock held.

Record recovery/action intents before candidate retirement or any preimage move. Restore only exact verified preimages to a stopped state. Before restoring any runnable canonical old application or startup-bearing plist, require positive inactive Login Item/startup-registration evidence for that exact old identity, or a separately already-authorized disable action plus verified inactivity. RunAtLoad=false/KeepAlive=false, no socket, label absence and a sent exit signal are insufficient. Never recreate/restore/enable Login Items or bootstrap/kickstart old code during rollback. If registration is enabled or unknown and no already-authorized supported disable path exists, preserve old app/plist in inert verified storage and report recovery incomplete. Do not restore first and discover auto-start afterwards.

A new coordinator after process loss does not inherit the old owner's capability. It authenticates its signed source, acquires existing original inode locks in standard order, reads complete durable control/journal/receipt evidence, and uses the accepted signed recovery path. Same-boot missing owners/PIDs/locks cannot retire custody or prove a never-admitted child; unresolved custody remains blocked. Prior-boot recovery requires direct differing kern.bootsessionuuid and the SPEC's interrupted/unknown receipts. Fully retired commands plus independently authenticated/drained host evidence may permit fixed-slot reconciliation under new exclusive recovery authority, but not ordinary admission or replay of a start command. Recovery never reconstructs the previous open-file description or claims it was continuously held across process death. Durable installation control provides the fence across that death.
