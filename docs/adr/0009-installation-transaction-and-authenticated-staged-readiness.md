# Installation transaction and authenticated staged readiness

## Concrete problem and scope

The accepted signed coordinator must retain operation exclusion while its newly promoted host proves readiness. The existing lifecycle authority permanently closes command borrowing before start and holds lifecycle EX, while host admission needs lifecycle SH. Command custody records also disappear between commands, leaving no installation-wide fence after coordinator death. The current staged-residue boolean does not authenticate a coordinator or prevent normal application startup. These are reachable installation blockers under ADR 0003 and the MVP boundary in ADR 0008.

Adopt the bounded installation amendment in [custody SPEC v4](../../.planning/artifacts/SPEC-29e9090a-7b77-443d-b953-9b1deef3bc60-437caba0-5fb9-5e51-8cc8-043efada242f-v4.md). Reuse the existing installer, custody registry/catalog persistence, bounded socket I/O and publisher verifier. No replacement installer, generic command framework, permanent service or new repository capability is authorized.

## Decision

1. Add mandatory, separately typed `custody/installation.json` and bounded action/preimage receipts under the existing catalog metadata guard. Persist intent before every consequential action, completion only after exact postimage validation and fsync. Missing or unknown evidence refuses admission. Initial state is fenced. Recognized older state gains this control only through authenticated exclusive migration. Per-command records cannot substitute for the transaction fence.
2. Consume the original installation owner once. Close old borrowing permanently and require actual registry removal, resource release, terminal fsync, direct-child reap and all expected EOF before changing phase. The original operation EX open-file description stays held continuously. Never reopen it, unlock a duplicate, convert a lock or replace its inode.
3. Permit only this consumed owner to close its last admission descriptions and acquire fresh descriptions of the same validated existing namespace/lifecycle inodes, nonblocking, while retaining original operation EX. Staging uses namespace SH/lifecycle SH and no run lease. Stopped ordinary restoration reacquires lifecycle EX; namespace-moving rollback reacquires namespace EX then lifecycle EX. No catalog guard, registry callback or authority mutex spans this acquisition. Failure retains the operation/fence and performs no restoration. Initial legacy migration still begins in ordinary order without lower-order locks held.
4. Add closed staged-start and staged-stop custody modes. Start permits exact promoted-candidate bootstrap/kickstart and fixed diagnostics. Stop permits only that authenticated candidate's exit/bootout and fixed diagnostics. Observation remains read-only and cannot bypass pending evidence. Existing command kinds, inherited descriptors, ownership, deadlines and cleanup rules remain.
5. Use a narrow coordinator-owned readiness socket with exact durable endpoint identity and a bounded session. Both sides authenticate kernel audit-token peer code against the exact candidate app/coordinator CDHashes, team and identifiers. Metadata, same UID, PID, nonce or a held-lock observation alone is not authority. The host receives no operation lease and enters a distinct readiness-only branch before AppKit/delegate, repository, policy, worker or network activity. Unsupported native authentication fails closed; no PID fallback is allowed.
6. Retire all start/diagnostic commands and verify launch/candidate/state convergence before durable readiness commit. Only then notify the authenticated host to begin normal startup. Original operation EX blocks repository/read/run work until cleanup. A committed receipt is historical evidence on subsequent boots; it is not a reusable live-coordinator capability. Postcommit recovery repairs forward. The exact receipt chain and allowed residual layout remain required.
7. Before rollback, close starts, fully retire commands, authenticate/drain the candidate and regain exclusive admission. Restore only verified preimages to a stopped state. Never restart old code or replay startup registrations. Enabled or unknown old startup routes require supported positive inactivity proof or an already-authorized disable action and verified inactivity; otherwise preserve the old bytes inert and report incomplete recovery. A plist with disabled RunAtLoad/KeepAlive is insufficient proof.

## Narrow precedence and unchanged gates

This decision prospectively amends only the installation scope and lock-order clauses identified by SPEC v4. The namespace rollback reentry above is the sole exception to ADR 0003's no-lower-order-lock condition; initial migration and every ordinary operation retain their prior ordering. Frozen ADRs and specifications remain unchanged. No general observation exception, arbitrary path writer, lost-owner adoption, signal-by-metadata authority, scope reopening or command replay is permitted.

The five-second readiness observation remains one shared absolute budget, and all existing command and repository deadlines remain unchanged. Qualification must cover command-free crash cuts, missing control, partial atomic writes, exact receipt reconciliation, zero-alias transfer, contention/substitution, wrong live peers, session loss before/after commit, pending retirement, failed stop and inert rollback. Native audit-token/socket behavior remains an explicit implementation and supported-host test gate.

This is an independently reviewed prospective architecture decision under delegated execution authority. It establishes no code correctness, complete CI, release, installation, startup choice or operator acceptance. ADR 0008's post-MVP backlog and all separate signing, publication, migration and focused acceptance gates remain open.
